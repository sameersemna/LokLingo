# LokLingo — Agentic Improvement Roadmap

Generated by a full-repo architecture audit (Go backend, React frontend, Python OCR service, e2e/infra) on 2026-09-12. Each task below is written to be executed by an autonomous agent in a fresh session with no other context beyond this file and the repository itself.

## Executive Overview

LokLingo is a three-service self-hosted translation platform (Go/Fiber backend, React 19 frontend, Python/FastAPI OCR microservice) with genuinely strong engineering hygiene in places: the backend follows constructor injection and structured logging conventions almost everywhere, the team has already run prior cleanup passes (documented in `.agentrules`/`IMPROVEMENT_LOG.md`), and there's real defensive code (path-traversal guards, constant-time token comparison, adaptive concurrency control).

The debt clusters in three places. First, **two monoliths**: `ocr-service/app.py` (2,101 lines — the entire OCR service in one file) and `backend/jobs/worker.go` (1,844 lines, with a single ~900-line `process` function) both carry disproportionate change risk and are undertested relative to their size. Second, **a partially-finished migration**: the frontend built centralized `utils/http.ts`/`utils/errors.ts`/`utils/storage.ts` abstractions per `.agentrules`, but roughly half the codebase was never migrated onto them — raw `fetch()`, `err instanceof Error` checks, and ad hoc `localStorage` keys still coexist with the "correct" pattern in the same files. Third, **silent configuration drift**: several `docker-compose.yml` env vars for OCR correction tuning don't match the names `app.py` actually reads, so they've been no-ops since introduction with no error surfaced anywhere.

Security-wise, the most consequential findings are a privileged internal-ops token that can end up baked into the public frontend bundle and persisted in plaintext `localStorage`, three job-read/SSE/download routes with no auth at all, and auth enforcement that silently no-ops unless `APP_ENV` is the exact literal string `"production"`. None of these are exotic — all are one-line-per-fix, high-value, low-effort.

Test coverage is the widest structural gap: the OCR service's substantial test suite (~1,000 lines) never actually runs in CI, the frontend has tests for only 6 of 54 source files (11%), and the backend's two largest/riskiest files (`worker.go`'s `process()`, `internal/httputil`) have no dedicated tests.

## Immediate Debt & Fixes (P0)

- [ ] **[SEC-01] Stop shipping the internal ops token in the public frontend bundle**
  - **Category**: Security
  - **Context & Impact**: `utils/http.ts` reads `import.meta.env.VITE_INTERNAL_TOKEN`. Vite inlines any `VITE_`-prefixed env var verbatim into the built JS at build time. If this var is set during a build, the token that gates privileged dead-letter-queue operations (list/replay jobs) ships in plaintext inside publicly servable JS, readable via view-source by any visitor.
  - **Target Files**: `frontend/src/utils/http.ts` (function `resolveInternalToken`), `frontend/src/api/deadletter.ts`, `frontend/src/DeadLetterOpsPanel.tsx`, build docs/`.env.example`.
  - **Proposed Implementation Steps**:
    1. Remove any code path that reads the internal token from `import.meta.env.*` at build time; the token must only ever come from runtime operator input.
    2. Confirm `DeadLetterOpsPanel.tsx`'s existing token-input field is the sole source of the token for the session (see SEC-02 for how it's stored).
    3. Grep the build pipeline (`Dockerfile`, CI, `.env*`) for any `VITE_INTERNAL_TOKEN` being set at build/image-build time and remove it.
    4. Document in README/AGENTS.md that this token must never be a `VITE_`-prefixed build var.
  - **Verification / Definition of Done**: `grep -r VITE_INTERNAL_TOKEN frontend/ --include=*.ts --include=*.tsx` returns no read of `import.meta.env`; `npm run build` output bundle (`frontend/dist/assets/*.js`) contains no literal token string when built with a real `INTERNAL_TOKEN` set in the environment.

- [ ] **[SEC-02] Stop persisting the internal ops token in plaintext localStorage**
  - **Category**: Security
  - **Context & Impact**: `DeadLetterOpsPanel.tsx` writes the operator-entered `X-Internal-Token` value to `localStorage` on every keystroke (`useEffect`) with no expiry or scoping. Any XSS elsewhere in the app, or a compromised lazy-loaded chunk, can read this token directly out of `localStorage.getItem(...)` and use it for privileged operations indefinitely.
  - **Target Files**: `frontend/src/DeadLetterOpsPanel.tsx`, `frontend/src/utils/storage.ts`.
  - **Proposed Implementation Steps**:
    1. Change the token field to hold the value only in component state (in-memory) for the current session by default.
    2. If persistence across reloads is genuinely required, gate it behind an explicit user opt-in checkbox and use `sessionStorage`, not `localStorage`.
    3. Remove the unconditional `useEffect` that writes to storage on every change.
  - **Verification / Definition of Done**: After entering a token and reloading the page without the opt-in, `localStorage.getItem("loklingo-internal-token")` (or equivalent key) returns `null`.

- [ ] **[SEC-03] Require auth on job read/SSE/output routes**
  - **Category**: Security
  - **Context & Impact**: `GET /api/v1/jobs/:id`, `GET /api/v1/jobs/:id/events`, and `GET /api/v1/jobs/:id/output` have no auth middleware in `main.go`, unlike write routes (`WriteAPIAuth`) and metrics/dead-letter routes (`InternalToken`). Job IDs are UUIDv4 and not enumerable, but anyone who intercepts or guesses a job ID can read translated text, stream live progress, or download output with zero authentication — inconsistent with every other stateful endpoint.
  - **Target Files**: `backend/main.go` (route registration block, look for `/api/v1/jobs/:id`), `backend/middleware/write_api_auth.go`, `backend/handlers/jobs.go`.
  - **Proposed Implementation Steps**:
    1. Decide the intended security model: either these routes require `WriteAPIAuth` (or a new lighter read-scoped token), or the UUID itself is the intended capability token — pick one and make it explicit in code comments.
    2. If auth is required, add the appropriate middleware to these three route registrations in `main.go`.
    3. Update any frontend/e2e code that calls these routes to include the required header.
  - **Verification / Definition of Done**: A request to `GET /api/v1/jobs/:id` without the required credential returns 401/403 (if auth model is chosen), and existing e2e tests covering job polling still pass with credentials attached.

- [ ] **[SEC-04] Fail closed when APP_ENV isn't recognized, not just when it isn't literally "production"**
  - **Category**: Security
  - **Context & Impact**: `config.Validate()` only enforces non-empty/strong `WRITE_API_TOKEN`/`INTERNAL_TOKEN` when `AppEnv == "production"` exactly. Any other value (a typo like `"prod"`, or `"staging"`) silently defaults both tokens to empty and turns `WriteAPIAuth`/`InternalToken` middleware into no-ops, opening every protected endpoint with no warning.
  - **Target Files**: `backend/config/config.go` (functions `Validate`, `weakProductionSecrets`).
  - **Proposed Implementation Steps**:
    1. Define an explicit enum/allowlist of recognized `AppEnv` values (e.g. `development`, `staging`, `production`).
    2. Require strong tokens for every value except an explicit, exact-match `development`.
    3. Fail startup (return an error from `Validate()`) for any unrecognized `AppEnv` value rather than silently treating it as non-production.
  - **Verification / Definition of Done**: Starting the backend with `APP_ENV=stagng` (typo) and empty tokens fails at startup with a clear config error instead of booting with auth disabled; add a config test asserting this.

- [ ] **[SEC-05] Remove hardcoded LAN hostname from CORS allowlist**
  - **Category**: Security
  - **Context & Impact**: `main.go`'s `allowLANOrigin` hardcodes `host == "promaxgb10-6116"` as an always-allowed CORS origin alongside legitimate localhost/private-IP checks. If this code is ever deployed to a shared or public environment, this is a permanent, unremovable-without-rebuild CORS bypass for a specific dev hostname.
  - **Target Files**: `backend/main.go` (function `allowLANOrigin`), `backend/config/config.go`.
  - **Proposed Implementation Steps**:
    1. Add an `AllowedOrigins` (or similar) config field read via `config.Load()`.
    2. Remove the hardcoded hostname literal from `main.go`; move it to `.env.development` as a configured value instead.
    3. Ensure production `.env.production` does not include this dev hostname.
  - **Verification / Definition of Done**: `grep -r promaxgb10 backend/*.go` returns no matches; CORS behavior for the dev LAN host is unchanged when the env var is set locally.

- [ ] **[OCR-01] Fix OCR PDF route blocking the FastAPI event loop**
  - **Category**: Performance
  - **Context & Impact**: `ocr_pdf` in `ocr-service/app.py` (around line 1992) is declared `async def` but calls the fully synchronous, CPU-bound `_ocr_pdf_file` directly. This blocks the event loop for the entire PDF processing duration (potentially minutes for large PDFs), starving all other concurrent requests including `/health`, while the sibling `ocr_image` route (plain `def`) correctly gets threadpool offload from Starlette.
  - **Target Files**: `ocr-service/app.py` (function `ocr_pdf` and its route decorator, `_ocr_pdf_file`).
  - **Proposed Implementation Steps**:
    1. Either change `ocr_pdf`'s signature from `async def` to plain `def` so Starlette offloads it to its threadpool automatically, or explicitly wrap the `_ocr_pdf_file(...)` call in `await run_in_threadpool(_ocr_pdf_file, ...)`.
    2. Verify no `await`-only code (e.g. httpx async calls to the LLM correction service) inside the PDF path is lost/broken by the signature change — if such awaits exist, use the `run_in_threadpool` wrapper approach instead of the plain-`def` approach.
    3. Load-test: issue a large PDF OCR request and confirm `/health` still responds promptly during processing.
  - **Verification / Definition of Done**: With a large (50+ page) PDF OCR request in flight, `curl http://localhost:<ocr-port>/health` returns promptly (<1s) instead of hanging until the PDF job completes.

- [ ] **[OCR-02] Fix silently-broken OCR correction env var names**
  - **Category**: Architecture
  - **Context & Impact**: `docker-compose.yml` sets `OCR_CORRECTION_RETRIES`, `OCR_CORRECTION_LOW_CONFIDENCE_THRESHOLD`, and `OCR_CORRECTION_MAX_CHUNK_BLOCKS`, but `ocr-service/app.py` actually reads `OCR_CORRECTION_MAX_RETRIES`, `OCR_CORRECTION_BLOCK_CONFIDENCE_THRESHOLD`, and `OCR_CORRECTION_CHUNK_CHARS` — none of the names match, so these three operator-facing tuning knobs have been dead since introduction. Additionally `OCR_CORRECTION_TIMEOUT` defaults to the string `"8.0"` in compose but is parsed with `int(...)` in `app.py`, causing a `ValueError` and silent fallback to a 25s default on every startup.
  - **Target Files**: `docker-compose.yml` (OCR service env block, lines ~68-71), `ocr-service/app.py` (functions reading `OCR_CORRECTION_*` env vars, around lines 71-74).
  - **Proposed Implementation Steps**:
    1. Rename the compose env vars to exactly match what `app.py` reads: `OCR_CORRECTION_MAX_RETRIES`, `OCR_CORRECTION_BLOCK_CONFIDENCE_THRESHOLD`, `OCR_CORRECTION_CHUNK_CHARS`.
    2. Change `OCR_CORRECTION_TIMEOUT` default in compose from `"8.0"` to an integer-parseable value (e.g. `"8"`), or fix `app.py`'s `_get_env_int` to tolerate float-formatted strings.
    3. Audit `docker-compose.dev.yml`/`docker-compose.prod.yml`/`docker-compose.ci.yml` for the same stale names.
    4. Add a startup log line in `app.py` echoing the resolved values of all `OCR_CORRECTION_*` settings so future mismatches are visible immediately instead of silently falling back.
  - **Verification / Definition of Done**: Set a non-default value for each of the three renamed vars in `docker-compose.dev.yml`, start the stack, and confirm via the new startup log line (or `/health` diagnostics) that the configured value — not the default — is in effect.

- [ ] **[OCR-03] Add a size cap on the JSON base64 image OCR endpoint**
  - **Category**: Security
  - **Context & Impact**: `/ocr/image` and `/api/v1/ocr` decode `req.image_b64` and call `Image.open(...)` with no explicit size check, unlike the PDF upload paths which all enforce `MAX_PDF_UPLOAD_BYTES`. A large or maliciously crafted base64 payload (or a decompression-bomb-style image) can consume unbounded memory/CPU with no server-side guard.
  - **Target Files**: `ocr-service/app.py` (`OCRImageRequest` model and its route handler, and wherever `base64.b64decode`/`Image.open` is called for the JSON image path).
  - **Proposed Implementation Steps**:
    1. Add a `MAX_IMAGE_UPLOAD_BYTES` env-configurable constant (mirroring `MAX_PDF_UPLOAD_BYTES`).
    2. Check `len(decoded_bytes)` against this cap immediately after `base64.b64decode`, before calling `Image.open`, and return 413/400 if exceeded.
    3. Set `Image.MAX_IMAGE_PIXELS` (or a manual pixel-count check after opening) to guard against decompression-bomb-style images regardless of byte size.
  - **Verification / Definition of Done**: A request with an oversized base64 image payload returns a clean 4xx error instead of consuming excessive memory; add a unit test in `test_app.py` asserting this.

## Architectural & Refactoring Tasks (P1)

- [ ] **[BE-02] Decompose `jobs/worker.go`'s `process()` into per-job-type pipelines**
  - **Category**: Architecture
  - **Context & Impact**: `Worker.process` is a single ~900-line function (of a 1,844-line file) handling PDF/image/text branching, OCR fallback, chunking, rendering, and caching in one body. This is the highest cyclomatic-complexity, highest change-risk function in the backend, and has no dedicated `worker_test.go` covering its full branch matrix.
  - **Target Files**: `backend/jobs/worker.go`, `backend/jobs/worker_image_test.go`, `backend/jobs/worker_pdf_test.go`.
  - **Proposed Implementation Steps**:
    1. Extract `processPDF`, `processImage`, and `processText` as separate methods on `Worker`, each handling only its job-type-specific branching.
    2. Factor the shared chunk-translation logic (currently interleaved across branches) into a common helper called by all three.
    3. Keep `process()` as a thin dispatcher that selects the right pipeline based on job type.
    4. Add `worker_test.go` covering the dispatcher and any branch not already covered by the image/PDF test files (OCR-only mode, layout-mode PDF stub, adaptive concurrency reduction, chunk-checkpoint resume, dead-letter classification).
  - **Verification / Definition of Done**: `go test ./backend/jobs/... -cover` shows increased coverage on the new pipeline functions; `process()` (or its replacement dispatcher) is under 100 lines.

- [ ] **[BE-03] Clarify or fix the OCR provider fallback chain's fake multi-engine semantics**
  - **Category**: Architecture
  - **Context & Impact**: `internal/services/ocr_provider_chain.go` wires `PaddleOCRProvider` and `TesseractProvider` to the same `ocrBaseURL`, and neither ever sends a `provider`/`engine` field in the request body. "Falling back from Paddle to Tesseract" is actually just re-calling the identical HTTP endpoint with an identical payload — this is a retry mechanism, not real engine diversity, contradicting what `OCRProvider`/`providerOrder` implies to a reader.
  - **Target Files**: `backend/internal/services/ocr_provider_chain.go`, `backend/internal/services/ocr_client.go`.
  - **Proposed Implementation Steps**:
    1. Decide the intended behavior: either pass a `provider`/`engine` parameter through to the OCR service so it actually selects a different engine per attempt, or rename/document the abstraction as a retry-with-backoff mechanism rather than a multi-engine fallback.
    2. If real engine selection is wanted, extend the OCR service's request schema to accept an engine hint and thread it through `runLegacyPDFProvider`/`runLegacyImageProvider`.
    3. Update code comments and `AGENTS.md`/`.agentrules` if the semantics change.
  - **Verification / Definition of Done**: A code comment or doc update makes the actual behavior (retry vs. real fallback) unambiguous to the next reader; if engine selection is implemented, a test confirms different provider tiers produce different request payloads to the OCR service.

- [ ] **[BE-04] Remove direct `os.Getenv` call in OCR provider chain constructor**
  - **Category**: Architecture
  - **Context & Impact**: `internal/services/ocr_provider_chain.go` reads `os.Getenv("OCR_PROVIDER")` directly inside a constructor, bypassing the mandatory `config.Load()` convention. It's also functionally dead since `main.go` always passes a non-empty `cfg.OCRProvider`.
  - **Target Files**: `backend/internal/services/ocr_provider_chain.go`.
  - **Proposed Implementation Steps**:
    1. Remove the `os.Getenv` fallback; require the caller-supplied config value only.
    2. Confirm `main.go` always passes `cfg.OCRProvider` through the constructor with no gap.
  - **Verification / Definition of Done**: `grep -rn "os.Getenv" backend/internal backend/services backend/jobs backend/handlers` returns no hits outside `config/` and test files.

- [ ] **[BE-05] Fix readiness handler creating a new Redis connection pool per request**
  - **Category**: Performance
  - **Context & Impact**: `handlers/readiness.go`'s redis check creates a brand-new `redis.Client` (fresh connection pool) on every single `/ready` call and closes it immediately after one `Ping`. Under a probe hitting this every few seconds, this is a full TCP handshake per probe instead of reusing the existing job-store's Redis pool.
  - **Target Files**: `backend/handlers/readiness.go`, `backend/jobs/store.go`, `backend/main.go` (wherever `ReadinessHandler` is constructed).
  - **Proposed Implementation Steps**:
    1. Change `NewReadinessHandler` to accept the existing `jobs.Store`'s underlying Redis client (or a shared health-check client) via constructor injection instead of creating its own.
    2. Remove the per-request `redis.NewClient`/`Close()` pair.
  - **Verification / Definition of Done**: `grep -n "redis.NewClient" backend/handlers/readiness.go` returns nothing; readiness checks still correctly report unhealthy when Redis is down (verify with a test that stops Redis mid-test).

- [ ] **[BE-06] Replace sleep-polling long-poll in synchronous image translate with event-driven wait**
  - **Category**: Performance
  - **Context & Impact**: `handlers/translate.go`'s `TranslateImage` implements a synchronous wait as `for { ...; time.Sleep(600ms) }` inside the HTTP handler goroutine, blocking a Fiber worker for up to 120s per request. Bounded by `InflightGate` so not unbounded, but it wastes goroutine/scheduler time compared to an event-driven wait.
  - **Target Files**: `backend/handlers/translate.go` (function `TranslateImage`), `backend/jobs/store.go`.
  - **Proposed Implementation Steps**:
    1. Introduce a Redis pub/sub channel (or equivalent condition variable) keyed on job ID that the worker publishes to on job completion.
    2. Replace the `time.Sleep` polling loop with a subscribe-and-wait (with the same 120s timeout as an upper bound).
    3. Confirm the SSE `/events` endpoint (which likely already does something similar) can share this mechanism.
  - **Verification / Definition of Done**: Load test showing reduced average latency-to-response for completed jobs, and reduced Redis polling QPS during high concurrent sync-image-translate load.

  - **Target Files**: `backend/internal/services/ocr_client.go`, `backend/internal/services/ocr_provider_chain.go`.
  - **Proposed Implementation Steps**:
    1. Create `ocr_client_interface.go` containing just the `OCRClient` interface; move implementation to remain in `ocr_client.go`.
    2. Create `ocr_provider_interface.go` containing just the `OCRProvider` interface; move `chainedOCRClient`/`PaddleOCRProvider`/`TesseractProvider` implementations to remain in `ocr_provider_chain.go`.
  - **Verification / Definition of Done**: `go build ./...` passes; interface and implementation live in separate files consistent with `services/interface.go`'s pattern.

- [ ] **[BE-09] Add request-id validation to prevent log injection**
  - **Category**: Security
  - **Context & Impact**: `middleware/requestid.go`'s `RequestID()` trusts a client-supplied `X-Request-ID` header verbatim with no format/length validation, and it flows directly into every structured log line and correlation ID used for dead-letter/metrics correlation. An attacker can inject arbitrarily long or control-character-laden values into logs, or spoof correlation IDs to conflate unrelated requests.
  - **Target Files**: `backend/middleware/requestid.go`, `backend/handlers/jobs.go` (correlation ID derivation).

- [ ] **[FE-02] Finish the storage-key centralization migration**
  - **Category**: Code Health
